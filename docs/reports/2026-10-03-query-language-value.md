# MiniArch 声明式查询层：价值证据与立项边界

日期：2026-10-03。结论：**有证据支持受限声明式查询优化层的可行性验证；没有证据支持直接承诺完整 SQL 产品或“所有查询全局最优”。**

## 给老板的一段话

> MiniArch 已经把数据存得很快，但用户仍要自己决定如何筛选、批量统计、关联和排序。项目内已有卡牌分组、逻辑 ID 关联、相同请求合并扫描的真实需求。在实际 MiniArch World 上的同语义合成实验中，批量统计、Top-K、逻辑 key 关联的候选策略，相比合理但不适合该负载的手写方案，分别获得约 8.8、12.7、7.3 倍的查询阶段加速，且计入了索引重建和结果写出。单 key 和大 K 的反例又证明：没有一种方案始终最好。因此值得验证的产品是“用户声明完整结果需求，系统替他选择并生成合适的执行策略”，而非仅增加 SQL 语法。是否需要文本 SQL，还取决于运行时查询或非 C# 消费者需求；C# 声明式 DSL 也能承载相同优化能力。

## 1. 证明的对象与未证明的对象

本次没有实现语言，没有修改 Core；只在独立 [QueryPlan.ValueLab](../../tools/perf/QueryPlan.ValueLab/README.md) 中比较手写物理执行策略。

已经证明：

1. 仓库中存在比组件存在性过滤更复杂的查询组织需求。
2. 对同一结果，执行策略可以造成显著差异，不仅是 GC 或 Debug/Release 差异。
3. 用户即使使用 chunk、复用缓冲区、消除明显分配，仍可能选错算法。
4. 最快候选会随查询次数与 K 变化，收益幅度也受 key 范围和分布影响；需要管理的是这些选择。

尚未证明：

- 尚不存在的编译器能自动生成这些执行器，且没有明显额外开销。
- SQL 文本优于 C# 声明式 API，或是实现优化的唯一必要形式。
- 外部项目实际经常出现本实验的数据规模，或研发投入已有商业 ROI。
- 候选集合之外不存在更好的算法；未测试 Quickselect、radix sort 等。

**“这些问题值得由公共查询层解决”与“必须做完整 SQL”是两个不同命题。**

真实项目补充见 [GodBrave 查询需求与编译摊销调查](2026-10-03-godbrave-query-language-value.md)：已确认实际调用形态、现行规模与既有 IR/缓存；游戏当前性能、编译成本与端到端收益仍未测量，不能继承本报告的合成倍数。

## 2. 需求不是凭空想象：仓库中的三个事实

| 真实需求 | 源码证据 | 用户已经在手写什么 | 证据边界 |
|---|---|---|---|
| 卡牌按区域、持有者收集/分组 | [CardCollector.cs](../../tests/HeroPipeline.Tests/GameplayEcs/Cards/CardCollector.cs)：`CollectInZone`、`GroupInZoneByOwner` | chunk 筛选、parent 关联、Dictionary 分组、List 输出；两种查询形态有两份组织代码 | 证明需求存在；下面的整数 zone Count/Sum 实验不是该卡牌系统的端到端测速，也没有比较 hierarchy children 访问路径 |
| 每颗追踪弹按逻辑玩家 ID 找目标位置 | [HomingBulletSteerSystem.cs](../../samples/BulletLockstep.Demo/Systems/HomingBulletSteerSystem.cs)：`Run`、`FindPlayerPosition` | 外层实体循环内再次 Query/Get，按值查另一个实体集合 | 证明逻辑 key 关联需求存在；当前 demo 玩家很少，不能据此声称它现在存在性能瓶颈 |
| 相同碰撞条件的多个请求共享候选扫描 | [CollisionSystem.cs](../../tests/HeroPipeline.Tests/GameplayEcs/Collision/CollisionSystem.cs)：`CollectGroups`、`ProcessGroup` | GroupKey 去重、列表池、每组一次扫描、向每个请求分发结果 | 证明共享查询工作的代码已由应用承担；本次未测此系统，也未证明通用语言能自动替代其业务副作用 |

额外的 Top-K 是常见候选需求（如排行榜、最优目标、筛选列表），但**尚未找到本仓库的实际 Top-K 调用方**，不能把它包装成已确认客户需求。

## 3. 四个可复现例子

下面均为最终退出码明确为 0 的独立复核运行的三窗口 median，单位 **ms/操作**，N=100,000、64 个唯一逻辑 target key、uniform 分布。完整 66 行数据、min/max、B/op 见 [原始 CSV](2026-10-03-query-plan-value.csv)。

### 例 A：筛选并返回字段——简单查询也容易走昂贵路径

需求：返回 Active 且 Score>1024 的 Entity、Score、Weight。

没有更高层的查询表达，用户可能先得到 Entity 列表，再逐个 Get 要返回的字段。改进后可以边遍历实体边输出；更好的现有写法则直接从 chunk 列筛选并输出。

| 方案 | 时间 |
|---|---:|
| Entity 列表后 Get | 2.629 |
| Entity 融合筛选/输出 | 1.022 |
| Chunk 融合筛选/输出 | 0.292 |

候选 chunk 方案相对前两者快 **9.01× / 3.50×**。所有方案使用复用缓冲区，测得 0.0 B/op，收益不是靠打败不断 new List 的方案。

**价值等级：基础便利，不足以单独立项。** 熟练用户已经能用现有 API 写出同样的 chunk 循环；编译层在这里应生成等价循环，而不是宣称超越它。文档、示例或普通辅助 API 也可能解决此问题。

### 例 B：一批 key 的统计——把 Q 次遍历变成一次聚合

需求：为指定的 64 个 zone，各返回 Count 和 Sum(Weight)；没有成员的请求 key 也返回零。

自然写法：对每个请求 key 扫一次匹配 chunk。合理优化：一次扫描，用复用 hash 表聚合后输出请求 key。若 schema 明确 key 在有限范围内，可选择 dense 聚合。

| 方案 | 时间 |
|---|---:|
| 64 次 chunk 扫描 | 4.815 |
| 一次 hash 聚合 | 0.545 |
| 已知有界 key 的 dense 聚合 | 0.119 |

一般 hash 方案快 **8.83×**；有界特化快 **40.38×**。Q=512 时，重复扫描 38.669ms，一次 hash 聚合 0.549ms，约 **70.40×**；合成负载的工作站数据不作为精确 SLA。

核心变化不是更快的 for，而是把约 `Q×N` 次检查变成 `N` 次聚合和 `Q` 次输出。只求统计时，还不应该先为每个桶存 Entity 列表。

**价值等级：高。** 用户需认识批量性、选择聚合而非建实体桶、管理 scratch 和零结果语义。有了完整的批量结果描述，这些选择可以由查询层集中处理。若用户每次只提交一个独立查询，系统看不到整批需求，则不能自动获得这种跨请求收益。

### 例 C：过滤后 Top-K——用户不应每次都全量排序

需求：过滤后按 Score 降序、Entity.Id/Version 升序，返回前 10 条完整结果；分数相同必须有确定的 tie-break。

| 方案 | 时间 |
|---|---:|
| Chunk 扫描后全量排序 | 5.504 |
| 容量为 K 的 heap，按排序语义输出 | 0.434 |

候选 heap 方案快 **12.67×**。不是只返回 K 个 ID：筛选、维护候选、返回 Entity/Score/Weight、有序输出均计时。正确性比较完整有序结果，包含同分数据。

典型成本从 `M log M` 变为扫描加 `M log K + K log K`，M 为过滤命中数。候选方案同时把部分字段读取推迟到确实进入候选时。

**价值等级：高，但需求待确认。** 用户需要处理候选替换、输出顺序、同分规则，并根据 K/M 决定是否值得用 heap。标准算法可以手写，但不应该由每个业务查询反复重新选择、验证。

### 例 D：按逻辑 key 关联另一批实体——避免逐条重新找目标

需求：每条 item 按 TargetKey 找唯一 target，返回 Entity、Score、Target.X；没有对应 target 的行跳过。这对应 demo 的 HostId 目标解析形态，但不是整套追踪弹系统测速。

| 方案 | 时间 |
|---|---:|
| 每 item 再次 Query/Get target | 48.119 |
| 缓存 chunks 的嵌套遍历 | 4.356 |
| 重建 key→所需字段的投影 hash 索引，然后扫描 | 0.594 |
| 已知有界 key 的投影 dense 索引 | 0.292 |

一般 hash 方案比合理的 chunk 嵌套遍历快 **7.33×**，比自然的逐条 Query/Get 快 **81.00×**。最终 nested 的 min/max 为 4.309/4.379ms，hash 为 0.590/0.596ms。此前捕获存在明显工作站抖动，报告统一采用这次独立复核的数据；结论是显著机会，不是精确倍数保证。

核心变化：`每 item 重复找 target` → `每次稳定读取阶段先组织 target 的 key 与所需值` → `每 item 定位并直接输出`。索引每操作重建，已计入时间；没有假设它自动跟随 World 写入。

**价值等级：高。** 用户必须处理关系基数、缺失 key、投影内容、构建时机和有效期。普通 Dictionary、现有 FrameLookup 或专用辅助 API 同样能实现部分策略；语言的价值是组合和自动选择，不是发明这些数据结构。

## 4. 反例证明“选择”比“固定优化”更重要

| 相同语义但不同负载 | 实测 | 结论 |
|---|---|---|
| N=100,000/uniform，只查一个 zone | 直接扫描 0.076ms；全量 hash 聚合 0.548ms | 所谓“先建索引”反而慢 **7.20×** |
| N=100,000/uniform，Top 50,000 | 全量排序 5.478ms；heap 9.557ms | 固定 Top-K heap 反而慢 **1.74×** |
| N=10,000，只有两个 target | cached chunk nested 0.071ms；hash 0.061ms | 一般索引只节省约 0.009ms，不能靠这一个小场景支持昂贵语言工程 |
| 已经写成 Chunk 融合筛选/投影 | 本实验的候选与最佳已测试手写循环就是同一段代码 | 这里没有额外性能创新，不能虚构“编译语言打败最佳手写” |

这不是单一阈值的永久证明。hot 分布下关联优化的优势幅度与 uniform 不同；应在实际工作负载上验证选择规则，而不是写死“遇到等号就建 hash”“遇到 LIMIT 就上 heap”。

## 5. 难点到底转移给谁

用户需求 → 完整查询表达 → 绑定类型/字段/关系契约 → 选择候选访问策略 → 一次或分阶段执行 → 返回指定形状的结果。

需要掌握的状态只有这些：

- 权威 World 数据，以及本次读取是否稳定。
- 请求 key 数、K、输出字段和排序/缺失值契约。
- 可合法使用的访问路径：组件筛选、直接实体定位、扫描、明确有效的派生索引。
- key 的范围、唯一性和候选策略成本；不得把未声明的性质当事实。

语言真正可能替用户承担的是：融合筛选/输出、减少重复扫描、减少中间数据、选择聚合/排序/关联算法、在合法读取阶段管理临时结构。

不能隐藏的是业务语义：零结果是否保留、JOIN 是否一对多、同分怎么排序、结果观察哪一时刻。两次查询之间发生写入时不能随意合并；任意有副作用的用户回调也不能任意重排。

## 6. 建议的立项裁决

**建议批准：受限声明式查询层的下一阶段价值验证。暂不批准：完整 SQL 引擎实现。**

下一阶段的最小证明不是 parser 功能清单，而是：

1. 在至少两个实际使用项目中确认批量统计、Top-K、逻辑关联等需求的频率、规模和当前痛点。没有真实复杂需求，便利 API 可能足够。
2. 让同一声明式查询在正例/反例上生成或选择正确候选，保持结果、排序和读取边界一致。
3. 与这里同语义的手写候选比较，计入编译摊销、构建和结果成本。简单查询不得明显退化；不能只打赢 Entity/Get 或 LINQ。
4. 只有确认“运行时改查询、不重编译应用”或“非 C# 作者/工具使用查询”的需求后，才把 SQL 风格文本作为必要前端。否则 C# DSL 是同等有效的候选。

“最优”应限定为**已验证候选策略中，按当前信息选择合适方案，接近同语义优秀手写**。本实验不是全局最优证明。

从零重建产品，只需三个责任：**表达所需结果、选择已验证的执行策略、在明确边界内产出结果**。不要从“复制一套 SQL 数据库”开始。

## 7. 方法、复现与验证

- 机器：AMD Ryzen 7 5700X3D，16 逻辑线程；Windows 10.0.26100；.NET 8.0.31 / SDK 8.0.425；共享工作站，非专用隔离性能机。
- 使用真实 MiniArch World、两个 item archetype（有/无 Cold），原始 fixture 数据独立验证。
- N=10,000/100,000；2/64 个 target；uniform/80% hot 分布；Q=1/64/512；K=10/1000/较大 K。
- 包含查询、扫描、每操作索引重建、scratch 清理、排序、类型化输出写入。
- 排除 World setup、首次容量分配、预热；没有解析/编译实现，无法测量语言自身成本。
- 三个 350ms 窗口，策略顺序轮换，取 median，保留 min/max；每策略 300ms warmup。测量期间不并行运行项目测试。
- 正确性 **780 次完整结果比较通过**，覆盖空数据、未命中 key/target、重复 score、K=0/K>N、混合 archetype 和数据倾斜。
- 所有策略可复用容量，非 Top-K 测得 0.0 B/op；FullSort 的本实现测得 64.0 B/op，最终 heap 0.0 B/op。未证明 FullSort 分配不可消除。
- MiniArch.Tests Release：**1171 通过，0 失败，0 跳过**。
- 产品代码与既有测试未修改；不属于 Core/HeroPipeline 架构变更，未运行 HeroComing 架构性能门禁。
- **复跑漂移（2026-10-14，HEAD 69d6eda、同一 `Program.cs`、780/780 正确性仍通过）**：66 行中位比值 1.00，43 行在 ±5%、52 行在 ±10% 内，多数差异是共享工作站的 µs 级抖动。
- 唯一系统性变化是逐条 `Query/Get` 的朴素基线：uniform/100k 关联 48.12→21.02ms，hot/100k 19.06→8.53ms（≈2.2×，来自 69d6eda 合并 world query cache）。因此本文的关联倍数偏大：HEAD 上 hash vs nested 为 8.4×（本文 7.33×），hash vs 朴素逐条为 34×（本文 81×）；方向不变，绝对数字与倍数按 2026-10-03 快照读取，对外引用前应在当前 HEAD 复跑。
