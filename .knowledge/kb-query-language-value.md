# 声明式查询层价值验证

## 结论

- **受限声明式查询优化层值得进入下一阶段验证；完整 SQL 产品尚未获证据支持。** 这是价值评估建议，不是已批准的产品路线。
- 仓库已有卡牌分组、逻辑 key 关联、相同碰撞请求共享扫描的实际需求形态；这些调用方的业务组织逻辑当前由用户手写。
- 同语义 Release 合成实验表明，批量聚合、Top-K、逻辑关联存在显著的策略选择机会；单 key 与大 K 反例表明固定“优化”会退化。
- 语言前端不是加速来源；减少重复工作、中间结果与不适合负载的算法才是来源。C# 声明式 DSL 可以承载同样的优化。
- 数字、原始 CSV、机器信息、验证结果和源码证据以 [价值报告](../docs/reports/2026-10-03-query-language-value.md) 为单一事实来源，不在本页重复表格。
- [GodBrave 只读调查](../docs/reports/2026-10-03-godbrave-query-language-value.md) 确认了重复定位、批量观察与共享绑定需求，也确认其已有规则 IR、投影缓存和小规模现行负载；它不支持直接把合成倍数当成游戏收益。

## 这个模块是干什么的

- 这个模块负责：
  - 保存“为什么值得考虑声明式查询层”的可复现证据与反对证据。
  - 区分真实需求形态、合成工作负载收益、未来编译器能力三个不同命题。
  - 为后续语言/API 提案提供可被推翻的验证标准。
- 这个模块不负责：
  - 提供 SQL parser、binder、优化器或代码生成器。
  - 改变 World/Core 的查询、线程、借用或持久化契约。
  - 承诺自动持久索引、完整 SQL 兼容性、绝对最优或商业 ROI。

## 架构

- 核心组成：
  - `tools/perf/QueryPlan.ValueLab/Program.cs`：真实 World 上的手写候选执行器与独立 fixture-data oracle。
  - `tools/perf/QueryPlan.ValueLab/README.md`：测量边界、运行命令和排除范围。
  - `docs/reports/2026-10-03-query-language-value.md`：面向决策的完整报告。
  - `docs/reports/2026-10-03-query-plan-value.csv`：最终版本的三窗口 median/min/max/分配数据。
  - `docs/reports/2026-10-03-godbrave-query-language-value.md`：外部真实项目的查询主链、替代 helper、编译摊销与时序边界。
- 数据流 / 控制流：
  - 固定 fixture 构造 World 和独立原始记录。
  - 每次稳定读取阶段选择一个手写执行器；索引重建、scratch 清理与结果写入都计入操作时间。
  - 以相同结果契约比较投影、批量 Count/Sum、Top-K 与唯一逻辑 key 关联。
  - 在计时外比较完整结果，而非只比较 checksum 或命中数量。

## 决策

- 保持零 Core 入侵：实验只使用公开 World/Query/chunk API，不增加写入热路径状态。
- 不把手写候选的速度称为尚不存在的编译语言速度；语言生成质量与编译摊销需要另行证明。
- 不把最佳候选称为全局最优；候选集合尚未覆盖所有排序/选择/关联算法。
- 不以分配 List/Dictionary 的弱基线作为唯一对手；各策略允许同样的容量复用。
- 普通筛选/投影很容易写成现有 chunk 循环，本身不足以支撑昂贵语言工程。
- 实际项目的源码形态不等于性能热点。GodBrave 调查后的下一证据应是优秀 typed helper 与计划层的完整成本比较，而不是继续叠加合成加速例子。
- GodBrave 已有建局编译的规则 IR；新增查询计划不能重复领取既有规则数据化的价值。SQL 文本前端还需要独立的 authoring/工具消费者证据。

## 认知模型

- 理解这个模块时，应该把它看成：
  - “同一个所需结果在不同负载下应采用不同执行策略，公共查询层有机会承担这些选择。”
- 这个模块里最重要的抽象是：
  - **结果契约**：输出字段、排序、缺失 key、关系基数与观察时刻。
  - **候选执行策略**：不同物理实现，而不是不同业务结果。
  - **稳定读取阶段**：临时结构合法有效的边界，不是自动并发快照或 MVCC。
  - **三个寿命**：固定参数化计划可跨多次执行；派生索引与结果只在已证明有效的阶段复用。数据写入通常不需重编译，但可能需重建索引/重读结果。
- 常见误解：
  - SQL 字符串本身使查询变快 → 错；字符串只是需求表达。
  - 有索引一定快 → 错；一次查询的构建成本可能超过扫描。
  - 有 LIMIT 一定该用 heap → 错；K 接近命中数时可比全量排序更慢。
  - 已有需求源码说明本实验是整个系统加速 → 错；它只证明这些形态的合成查询阶段机会。

- 实验失败时先看：
  - `Correctness.Run`：完整输出 oracle、空数据、同分、缺失 target/key、K=0/K>N。

  - `Measure.Group`：预热、轮换顺序、计时与分配边界。

## 坑点

- Dense 候选依赖明确有界 key；任意稀疏大值不能直接索引数组。
- 关联实验只覆盖唯一逻辑 key；重复 key、一对多和 NULL 不在范围内。
- 每操作都重建索引，不能据此承诺跨 World 写入自动有效的持久索引。
- 分开执行且中间有写入的查询不能随意合并；碰撞业务副作用也不能凭查询等价随意重排。
- Top-K 同分顺序必须作为结果契约验证；仅比较命中集合不足以证明排序正确。
- 共享工作站存在噪音，需保留 min/max，不把少量样本当作精确 SLA。引用绝对倍数前需在当前 HEAD 复跑：引擎缓存改进会直接压低朴素基线（2026-10-14 复跑中逐条 `Query/Get` 比 2026-10-03 快约 2.2×，见报告 §7）。
- 输出写入计时，但首次容量分配与长期独立结果的额外复制不在测量内。
- 后续引入真实编译器后必须重新对齐同语义的优秀手写与完整成本，不能直接继承本次候选执行器的数字。
- 回本以新增编译/首用成本加索引维护差额，对比累计执行净节省；被现有缓存跳过的读取不算计划执行次数，共有的既有 IR 编译成本也不重复记入。
- 不可变 Program 的词汇/元数据查询可以提前绑定；跨实际提交的条件/目标观察不能随意融合，特别是 subject 反应会改变后续 ANY_CHARACTER 绑定时。
